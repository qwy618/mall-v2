# 商品域属性表设计（债务 1，兼债务 2 地基）

> 版本：2026-10-06 ｜ 范围：mall-v2 商品域
> 关联：`复刻计划/技术债与补记清单.md` 债务 1 / 债务 2、`复刻计划/商品域-建表参考版.sql`
> 上游影响：`mall-ai-agent` 的 `get_product_detail`（详情问答深度受限的根因）

---

## 1. 问题

### 1.1 现状盘点（实测）

| 维度 | 现状 |
| --- | --- |
| 表 | **无** `attribute` / `album` 表；规格存 `sku.sp_data VARCHAR(500)`，内容是 JSON 数组文本 |
| 规格存法 | `[{"key":"颜色","value":"黑色"},{"key":"容量","value":"32G"}]` |
| 规格名（全库实测） | **7 种**：`颜色` / `容量` / `尺寸` / `风格` / `内存` / `版本` / `系列`，按品类分散 |
| 数据量 | 38 product / 97 sku |
| 管理端 | 加/改 SKU 时「规格」是一个 **textarea 手敲 JSON**（`mall-admin-v2/src/views/product/index.vue:169`，placeholder 就是"规格 JSON，可空"）；无属性管理页 |
| C 端 | 详情抽屉只有「选择规格」（列 SKU，`portal-web/src/views/product/index.vue:172`），**没有「规格参数」展示区** |
| 详情接口 | `GET /product/{id}` → `ProductDetailVO{ product: ProductVO, skus: List<Sku> }`；`ProductVO` 只有 `id/productSn/name/pic/sale/status/lowestPrice` |
| 已有资产 | `portal-web/src/utils/spec.ts` 的 `formatSpec()` 已能兼容 4 种 `sp_data` 形态（**纯展示**，无结构解析） |

### 1.2 痛点（定位到具体后果）

1. **运营手敲 JSON，写错不报错**。key 写成"颜色 "（带空格）或"color"，没有任何校验；前端 `formatSpec()` 有兜底，会把畸形数据**原样渲染**，运营看不出来，直到用户投诉。
2. **按规格筛选做不到**。`WHERE sp_data LIKE '%黑色%'` 有两个问题：误命中（"深黑色"、"黑色彩壳"）、`%...%` 用不上索引。债务 2 要的"按颜色筛选手机"目前无法实现。
3. **C 端无商品参数展示**。像"上市年份""屏幕尺寸"这类**仅展示、不参与价格库存**的信息，现在**无处可放**，只能硬塞进 `sub_title`（255 字符）。
4. **助手详情问答做不深**。`get_product_detail` 只能返回 product + skus，模型拿不到结构化参数，`mall-ai-agent/docs/智能助手生产化设计.md` §8 已把这条列为助手的上游瓶颈。

### 1.3 `商品域-建表参考版.sql` 的评估：**不能照抄**

参考版 §「可选规格属性表」给了 `product_attribute` + `product_attribute_value` 两张表，但有两处硬伤：

| # | 缺陷 | 后果 |
| --- | --- | --- |
| 1 | `product_attribute` **没有 `category_id`** | 属性变成**全局池**。库里"颜色/容量"属手机、"尺寸/风格"属服饰，全局化后 T 恤的编辑页会冒出"容量"这种无关属性 |
| 2 | `product_attribute_value.value` 是**逗号分隔多值**（注释原文：`黑色,蓝色,褐色`），且只有 `product_id` 没有 `sku_id` | ① 逗号串是**"可选值清单"**的存法，不是"商品实际属性值"（一个商品一个属性就该一个值）；② 它是**商品级**的，**无法表达"哪个 SKU 是哪个值"** → 债务 2 的"按规格值筛选商品"**依然做不到** |

> 结论：参考版可以理解为「**参数**表 + 属性定义表」的雏形，但它把**规格**和**参数**混在一张表里了。规格（SKU 级、影响价格库存）与参数（商品级、仅展示）必须分开。

## 2. 核心决策：谁是"真源"

属性行与 `sp_data` 是**同一事实的两种表示**，必须先定谁是真源，否则一定会不同步。

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| **A（推荐）** | `sp_data` 为**真源**，属性行是**派生索引**（SKU 写入时同步拆解） | `sp_data` 已被 **8+ 处消费**（购物车快照 / 订单快照 / ai-agent / 前端 4 个页面 / `spec.ts`），改真源要动全链路；A 只需在写入时多写一张索引表，**向后兼容、可回滚** |
| B | 属性行为真源，`sp_data` 降级为派生展示 | 更"规范"，但要改 SKU 创建/编辑/快照/前端渲染全链路，风险与工作量都大 |
| C | 不建关系表，直接用 MySQL 生成列 + 索引抽 `sp_data` | 不现实：`sp_data` 是 `VARCHAR` 非 JSON 列，且规格 key 是**动态的**（7 种且会变），生成列要求列固定 |

**推荐 A**。代价是"两份表示需要一次写入同步"，用「事务内 delete + insert」+ 一条数据一致性校验 SQL 兜住。

## 3. 表设计（修正版 3 张）

### 3.1 属性定义表（加分类归属 —— 修掉参考版缺陷 1）

```sql
CREATE TABLE product_attribute (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY                   COMMENT '主键ID',
  category_id  BIGINT       NOT NULL                               COMMENT '归属分类，关联category.id（修掉参考版的全局属性池）',
  name         VARCHAR(64)  NOT NULL                               COMMENT '属性名，如：颜色 / 容量 / 上市年份',
  type         TINYINT      NOT NULL DEFAULT 0                     COMMENT '属性类型：0规格(影响价格库存,S选) 1参数(仅展示)',
  input_type   TINYINT      NOT NULL DEFAULT 1                     COMMENT '录入方式：0手工录入 1从列表选择',
  input_list   VARCHAR(500)                                        COMMENT 'type=0时的可选值清单，逗号分隔，如：黑色,蓝色',
  sort         INT          NOT NULL DEFAULT 0                     COMMENT '排序',
  create_time  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP     COMMENT '创建时间',
  UNIQUE KEY uk_category_name (category_id, name),                 -- 同一分类下属性名唯一：防"颜色"/"颜色 "并存
  KEY idx_category (category_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT '商品属性定义表';
```

### 3.2 商品参数值表（只服务 type=1 参数）

```sql
CREATE TABLE product_attribute_value (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY                  COMMENT '主键ID',
  product_id    BIGINT       NOT NULL                              COMMENT '商品ID，关联product.id',
  attribute_id  BIGINT       NOT NULL                              COMMENT '属性ID，关联product_attribute.id',
  value         VARCHAR(500) NOT NULL                              COMMENT '属性值（单值，如：2023 / 6.1英寸）',
  UNIQUE KEY uk_product_attr (product_id, attribute_id),           -- 一个商品一个属性只有一个值
  KEY idx_attribute (attribute_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT '商品参数值表(type=1，仅展示)';
```

### 3.3 SKU 规格值表（债务 2 的依赖 —— 补上参考版缺陷 2）

```sql
CREATE TABLE sku_attribute_value (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY                  COMMENT '主键ID',
  sku_id        BIGINT       NOT NULL                              COMMENT 'SKU ID，关联sku.id',
  attribute_id  BIGINT       NOT NULL                              COMMENT '属性ID，关联product_attribute.id(type=0)',
  value         VARCHAR(255) NOT NULL                              COMMENT '该SKU在这个属性上的取值，如：黑色',
  UNIQUE KEY uk_sku_attr (sku_id, attribute_id),                   -- 一个SKU一个规格属性只有一个值
  KEY idx_attr_value (attribute_id, value)                         -- 按规格筛选走这个索引
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT 'SKU规格值表(由sku.sp_data派生)';
```

> **为什么规格不写 `product_attribute_value`**：规格是 **SKU 级**、参数是 **商品级**，粒度不同。这是参考版最根本的问题，也是"按规格筛选"必须补第 3 张表的原因（债务 2 说的 `sku_attribute_value` 正是这张）。

## 4. 同步策略

- **触发点**：mall-admin 的 `SkuServiceImpl` 在 **create / update / delete** 三处（都在事务内），解析 `sp_data` → 写 `sku_attribute_value`。
- **属性定义兜底**：拆解时按 `(category_id, name)` 查 `product_attribute`（category 由 `sku.product_id → product.category_id` 得到）；查不到则**自动建**一条 `type=0` 的记录（标记来源，避免运营没先配属性就存不了 SKU）。这样**存量 97 个 SKU 无需人工配属性**。
- **更新语义**：先 `DELETE FROM sku_attribute_value WHERE sku_id = ?`，再批量 INSERT（幂等，天然处理"规格值改了"）。
- **一致性校验**（写进验收脚本）：`SELECT COUNT(*) FROM sku WHERE sp_data IS NOT NULL AND sp_data <> '[]'` 应等于 `SELECT COUNT(DISTINCT sku_id) FROM sku_attribute_value`；不等即同步漏了。

## 8. P2 设计：按规格筛选商品（2026-10-07 定稿）

> 债务 2 的顺承。**前端已落地**（`portal-web`），后端待实现 —— 照 §8.1 的契约对接即可。

### 8.1 接口契约（前后端已对齐）

**① 列表加筛选参数**

```
GET /product/list?attrs=颜色:黑色|白色,容量:256GB&categoryId=19&pageNum=1&pageSize=10
```

- `attrs` 格式：`属性名:值|值`，多个属性用 `,` 分隔。
- 语义：**跨属性 AND**（黑色 且 256GB）、**同属性多值 OR**（黑色 或 白色）。
- 不传 / 空串 = 不筛选。
- ⚠️ 原 P2 草案写的 `?attrValue=黑色` **不可用**：索引 `idx_attr_value(attribute_id, value)` 最左前缀是 `attribute_id`，
  只给值必然全表扫；且**同名属性跨分类是不同 id**（库内「颜色」有 1/2/4/5/6/8/9 共 7 个）。
- ⚠️ **`categoryId` 必传**：因为上一条，不传分类就无法把属性名唯一解析成 `attribute_id`。
  不带 `categoryId` 时 `attrs` 直接按「空结果」处理（与 `/product/spec-filters` 的口径一致，
  也与前端一致 —— 面板本来就是按分类聚合的，不选分类时面板根本不出现）。
- ⚠️ **`attrs` 用 `,` `|` `:` 分隔**，与 `product_attribute.input_list` 的「逗号分隔」是同一条约定：
  规格取值里不能含这三个 ASCII 字符。全角 `｜`／`：` 不在分隔符之列 —— 库内
  `新品980｜NVMe PCIe3.0*4` 这类取值真的带全角 `｜`，别顺手 normalize。

**② 筛选面板（facet）**

```
GET /product/spec-filters?categoryId=19
→ [{ "attributeId": 1, "name": "颜色", "values": [{ "value": "黑色", "count": 12 }, ...] }, ...]
```

- 只返回 `type=0`（规格）的属性，按 `sort, id` 排序；`values` 按 count 倒序。
- 无数据返回 `[]`（前端据此整块隐藏面板）。
- `count` 本期为**静态计数**（该分类下的绝对值，不随已勾选项收敛）→ 见 §8.5。

### 8.2 反查 SQL（核心 · 已按 EXPLAIN 实测定型）

**① 属性名 → attribute_id（Service 层单表查询）**

```sql
SELECT * FROM product_attribute WHERE category_id = ? AND name = ?;  -- uk_category_name 唯一
-- 取到后还要校验 type = 0：type=1 的参数是商品级、不参与筛选
```

🔴 **必须用只读查询，不能复用 `resolveSpecAttributeId`** —— 那个方法查不到会「自动建属性定义」。
筛选是读路径，不该被一个拼错的属性名写脏数据。

**② 反查命中 SKU（`SkuAttributeValueMapper.selectSkuIdsBySpecGroups`）**

```sql
SELECT sav.sku_id
FROM sku_attribute_value sav
WHERE ( sav.attribute_id = 1  AND sav.value IN ('黑色','白色') )
   OR ( sav.attribute_id = 10 AND sav.value IN ('256GB') )
GROUP BY sav.sku_id
HAVING COUNT(DISTINCT sav.attribute_id) = 2   -- = 属性组数
```

- 🔴 **不能写成** `WHERE attribute_id IN (1,10) AND value IN ('黑色','256GB')`：
  那会命中「颜色 = 256GB」这种根本不存在的组合（跨列笛卡尔误配）。
- 🔴 **必须用 `COUNT(DISTINCT attribute_id)`**：同一属性传多个值时单个 SKU 也只有一行，
  用 `COUNT(*)` 会把「只满足一个属性」的 SKU 也算进来。
- 🔴 **刻意不 join `sku`**。实测四种形态的执行计划：

  | 形态 | type | key | 结论 |
  | --- | --- | --- | --- |
  | 单属性 `attribute_id=? AND value IN (?)` | `ref` | `idx_attr_value` | ✅ 最优 |
  | 双属性 OR 两组 | `range` | `idx_attr_value` | ✅ 走索引 |
  | 每属性一个 `EXISTS` 子查询（备选方案） | `index` | `idx_product`（全扫 97 行） | ❌ 用不上 `idx_attr_value` |
  | 反查后接 `JOIN sku` 再 join product | 优化器改选别的索引 | ❌ | join 会把好不容易用上的索引挤掉 |

  这就是实际实现是「先反查 sku_id → 再按 sku_id 批量读 sku」两步、而不是一条大 join 的原因。

**③ SKU → 商品 + 命中最低价（Service 层，一次 `selectBatchIds(skuIds)`）**

```java
List<Sku> skus = skuMapper.selectBatchIds(skuIds);      // 本来就要读 price
minPriceByProduct.merge(pid, price, BigDecimal::min);   // 命中规格那批 SKU 的最低价（验收 #8）
// keySet = 命中的 DISTINCT 商品 id
```

### 8.3 与现有 `/product/list` 的合流（实现后的实际形态）

- 分支不变：**有 keyword → ES**；否则 → DB（categoryId / brandId / 规格 + 分页）。
- 本期边界（决策 ④）：**规格筛选只在「无 keyword」的 DB 分支生效**；同时带 keyword 与 attrs 时
  忽略 attrs 并 `log.warn`。理由：ES 文档没有规格字段，硬做得改索引结构 —— 先收住范围，另记新债务。
- DB 分支：反查得到 `Map<商品id, 命中最低价>`，把 **keySet 作为 `w.in(Product::getId, ids)`**，
  然后**照常走 `selectPage`**。
  - ⚠️ 设计稿原先写「自行 `LIMIT` 再手拼 `Page`」——**实现时改了**：并回常规分页后，
    `total` 天然就是「再叠加 分类/品牌/上架 过滤之后的 DISTINCT 商品数」，
    省掉一个最容易算错（分页不重不漏）的环节。
  - 代价：反查会把**命中的全部商品** id 拉回来，而不是只拉一页。本库 38 商品无所谓，
    数据量大时按 §8.5 的覆盖索引 / 下推方案演进。
- **顺手补了 `w.eq(Product::getStatus, 1)`** —— 原先这条路径不滤 status，
  实测有 7 个 `status=0` 的下架商品会混进 C 端列表（`/product/similar` 一直是滤的，属漏网）。
- ⚠️ **id 集合为空要直接返空页**（`emptyProductPage`），绝不让 `in()` 收到空集合
  （会拼出 `IN ()` 语法错，与现有 `selectBatchIds(空)` 那个坑同源）。
- ⚠️ 属性名解析**失败即空结果**（不抛异常）：名字对不上 → 200 + 空列表。
- ⚠️ `attrs` 解析里 **重复属性名要合并**。若不合并，会出现两个同 `attribute_id` 的组 →
  `HAVING COUNT(DISTINCT attribute_id) = 2` 恒不成立 → **静默返回空结果**，是最难排查的一类 bug。
  实现上用 `Map<attributeId, LinkedHashSet<value>>` 承接，从结构上排除这种可能。
- 新端点 `GET /product/spec-filters` **免登录**：`SecurityConfig` 里 `/product/**` 已 `permitAll`，
  无需额外加白（这条是游客白名单铁律的检查点）。

**容错口径（实测确认）**：`属性名给全但值为空`（`颜色:`）与 `格式非法`（没有冒号）一律**跳过、不筛**
（结果 = 该分类全量），全程 200 不报错。理由是与前端 UI 的状态模型一致：
**「某属性没勾任何值」就等于「不约束这个属性」**（`buildAttrsParam` / `toggleSpec` 里最后一个值被取消时整个键就被删掉）。
注意这与「取值在库里不存在」（`颜色:靛青色` → 空结果）是**两件不同的事**，前者是"没给条件"，后者是"给了条件但无货"。
