## 1. 订单状态机（改造后终态）

```
        ┌──────────── 用户支付 ────────────┐
        │                                   ▼
  0 待付款 ──取消/超时──▶ 4 已关闭      1 已付款 ──后台作废──▶ 5 无效订单
        │                                   │
        │                                   │ 后台发货
        │                                   ▼
        │                              2 已发货 ──确认收货(手动/自动)──▶ 3 已完成
        │                                   │
        └──────────────▶ 4 已关闭           └──(完成后方可申请售后)
```

- **4 已关闭**：订单曾有效，被取消（用户主动 / 超时未支付）——已有行为，不动。
- **5 无效订单**：订单从未履约，被后台作废（已付款但发货前商品下架/缺货）——本次新增，语义与 4 明确区分。

## 2. 债务 11：订单自动确认收货

### 2.1 为什么不用 MQ

项目里已有的「订单超时取消」走 RabbitMQ 延迟队列（队列级 TTL=30 分钟）。但「发货 N 天后自动收货」的量级是**天**，队列级 TTL 不适合（需要为每天建队列且不可灵活改阈值）。故引入 `@Scheduled` 定期扫描——项目此前**没有 `@EnableScheduling`**，本次补上。

### 2.2 实现

| 文件 | 职责 |
|---|---|
| `portal/config/SchedulingConfig.java` | `@Configuration @EnableScheduling`，全局开启定时任务 |
| `portal/component/OrderAutoConfirmTask.java` | 扫描候选单 + 逐单调用 `completeOrder(id, "system")` |
| `portal/service/OrderService#completeOrder(Long, String)` | **抽取的公共完成逻辑**，手动确认与自动确认共用 |

**扫描条件**：`status=2 AND delivery_time IS NOT NULL AND delivery_time <= now - N天`，按 `delivery_time` 升序，`limit 每轮上限`。

**设计要点**：
- **起点用 `delivery_time`**（发货时间）而非 `create_time`——用户关心的是"到手多久"。
- **幂等靠状态机**：真正的流转在 `completeOrder` 里以原子条件 `UPDATE ... WHERE status=2` 完成，重复扫描/并发只生效一次（同时保证赠积分只发生一次）。
- **逐单 try-catch**：一条脏数据不中断整轮。
- **每轮限量**：防止单次大事务拖垮数据库。

**可配置参数**（`--mall.order.*` 覆盖，默认 7 天 / 10 分钟一轮 / 首轮延迟 60s / 每轮 200 单）：

```
mall.order.auto-confirm-days              自动确认收货天数，默认 7
mall.order.auto-confirm-batch             每轮最多处理单数，默认 200
mall.order.auto-confirm-initial-delay-ms  启动后首次执行延迟，默认 60000
mall.order.auto-confirm-interval-ms       两轮间隔，默认 600000
```

> E2E 用短间隔参数（`initial=8000 / interval=20000`）启动 portal 现场验证，验完全量包以默认参数重启。

## 3. 债务 8：无效订单（状态 5）+ 后台作废

### 3.1 DDL 012（`docs/sql/012_order_invalidate_refund.sql`）

`payment` 表加两列（存储过程按 `information_schema` 存在性守卫，可重复执行）：
- `refund_amount`：退款金额（订单作废时写入 = `orders.pay_amount`）
- `refund_time`：退款时间

`payment.status` 语义扩展为：**0 未支付 / 1 已支付 / 2 已退款**。

### 3.2 后台作废接口

`POST /order/invalidate/{id}`（body/param：`note` 备注）→ `admin OrderServiceImpl.invalidate(id, note)`。

**仅 `status=1`（已付款未发货）可作废**，原子 `1→5`（`affected=0` 即拒），随后一次性回滚全部副作用：

| 步骤 | 动作 | 目的 |
|---|---|---|
| 1 | 回滚库存：逐 item `sku.stock + quantity` | 库存归还 |
| 2 | 退回优惠券：`coupon_history` 命中本单的 `status 1→0`，清 `order_id/order_sn/use_time` | 券可再用 |
| 3 | 退回积分：`memberPointsService.refundConsumed(...)`（全额退回已抵扣积分，记 `TYPE_INVALID_BACK=5` 流水） | 积分归还 |
| 4 | 退款（Mock）：`payment` 命中本单 `status 1→2`，写 `refund_amount/refund_time` | 资金流水标记 |
| 5 | 记 `order_operate_history`：`INVALIDATE`，操作人 = 当前管理员 | 可追溯 |

> **不写这一步的代价**：会出现"钱退了但库存/券/积分没回来"的资损。

### 3.3 前端

- **管理端** `views/order/index.vue`：状态筛选加「无效订单」；`ORDER_STATUS_TEXT/TAG` 加 `5: '无效订单'`（`danger` 色）；`status=1` 行加「作废」按钮（弹窗填备注）；`apis/order.ts` 加 `invalidateOrder`；**状态列移到 ID 之后**（原在备注列之后，被操作列加宽挤到横向滚动区外，常驻可见性优先）。
- **C 端** `types/order.ts` + `views/order/list.vue` + `views/order/detail.vue`：状态文案/描述数组补第 6 位「已失效」；订单列表加「已失效」Tab；个人中心订单入口网格 `repeat(5→6, 1fr)`。

## 4. 共享模块 `mall-service`（跨模块积分能力）

### 4.1 为什么新建模块

赠分/回冲逻辑原本在 **portal**（`IntegrationService`），而「退货完成」「后台确认收货」在 **admin** 模块。两个应用都要用同一套口径，否则必然漂移。新增 **`mall-service`** 作为纯业务能力模块，`admin` 与 `portal` 共同依赖。

> 落点选择：新建模块（最规范，后续商品域等也能复用），而非塞进 `mall-mbg`（业务逻辑不该进数据层）或走 MQ（异步最终一致，工作量最大且此处不需解耦）。

### 4.2 模块结构

```
mall-v2/mall-service/
  pom.xml                         依赖 mall-common + mall-mbg + mybatis-plus + lombok
  src/main/java/com/macro/mall/service/
    MemberLevelService.java         会员等级（由成长值反推最高档 + 权益）  ← 从 portal 迁入
    impl/MemberLevelServiceImpl.java
    MemberPointsService.java        积分与成长值统一口径               ← 新建
    impl/MemberPointsServiceImpl.java
    vo/MemberLevelVO.java           等级视图                          ← 从 portal 迁入
```

- 父 `pom.xml`：`<module>mall-service</module>` + `dependencyManagement` 声明；`mall-admin`/`mall-portal` 各加依赖。
- 包名 `com.macro.mall.service`，两应用启动类 `scanBasePackages="com.macro.mall"` 自动扫到，无需额外配置。
- 原 portal `IntegrationService(+Impl)`、`MemberLevelService(+Impl)`、`vo/MemberLevelVO` **已删除**，`MemberController` / `OrderServiceImpl` 引用改指共享模块。

### 4.3 `MemberPointsService` 统一口径

```java
int POINTS_PER_YUAN = 100;          // 100 积分 = 1 元

int TYPE_GRANT        = 1;          // 交易完成赠送
int TYPE_CONSUME      = 2;          // 下单抵扣
int TYPE_RETURN_BACK  = 3;          // 退货扣回
int TYPE_ADMIN        = 4;          // 管理员调整
int TYPE_INVALID_BACK = 5;          // 无效单作废，退回已抵扣积分   ← 本期新增

consumeForOrder(memberId, orderId, orderSn, points);         // 下单抵扣（原子条件扣减，余额不足抛异常）
grantForOrder(memberId, orderId, orderSn, payAmount);        // 赠送：+积分 +成长值 +自动升级 +流水
revokeForReturn(memberId, orderId, orderSn, returnAmount);   // 退货回冲（见下）
refundConsumed(memberId, orderId, orderSn, points);          // 无效单退回抵扣积分
listHistory(memberId, pageNum, pageSize);                    // 流水倒序分页
```

### 4.4 退货回冲算法（债务 3 顺带闭环）

- **口径与赠送一致**：`回冲积分 = floor(退货金额 × 当前等级积分倍率%)`。
- **扣减原子且钳制**：`UPDATE member SET integration = GREATEST(integration − ?, 0) WHERE id=?`，**余额不足则扣到 0**，绝不扣成负数；返回实际回冲数。
- **成长值不回冲**：成长值代表历史消费，回冲会牵扯降级，收益低，本期不做。
- 落点：`admin OrderReturnServiceImpl.complete()`（退货单 `status 3→4` 时）调用 `revokeForReturn(a.getMemberId(), a.getOrderId(), a.getOrderSn(), a.getReturnAmount())`，记 `TYPE_RETURN_BACK=3` 流水。

### 4.5 后台代确认收货补赠积分

`admin OrderServiceImpl.complete()` 原把订单置 3 却**不赠积分**（只有 C 端确认收货才赠）→ 后台代确认收货时会员拿不到分。现改为与 C 端共用：原子 `2→3` 成功后调 `memberPointsService.grantForOrder(...)`，`recordHistory` 记 `CONFIRM`。

## 5. 并发与幂等小结

| 场景 | 手段 | 防的问题 |
|---|---|---|
| 自动确认收货重复触发 | `completeOrder` 内原子 `UPDATE ... WHERE status=2`，`affected==1` 才赠分 | 重复确认 → 重复赠分 |
| 后台作废重复点击 | 原子 `UPDATE ... WHERE status=1` | 重复回滚库存/券/积分 |
| 退货回冲 | 退货单 `status=3` 才可完成（状态机） | 重复回冲 |
| 积分扣减（抵扣/回冲） | `WHERE integration >= ?` 条件更新 + 钳制到 0 | 并发超用/扣成负数 |
| 积分/成长值累加 | `setSql("integration = integration + ?, growth = growth + ?")` | 并发互相覆盖 |

## 6. 验证（`scripts/e2e_order_closeout.py`，26 项）

- **A 自动确认收货**：造已发货单并回拨 `delivery_time` → 等定时任务 → `status=3`、积分按"赠送发生前等级倍率"到账、流水 `TYPE_GRANT`、操作人 `system`。
- **B 后台确认收货赠分**：`POST /order/complete/{id}` → `status=3` + 赠分 + 流水。
- **C 无效单作废**：先抵扣积分下单并支付 → `POST /order/invalidate/{id}` → `status=5`、库存回滚、券退回、抵扣积分退回（`TYPE_INVALID_BACK`）、`payment.status=2` 且有退款金额/时间、重复调用第二次被拒。
- **D 退货回冲**：收货赠分 → 申请售后 → 后台完成退货 → 按退货额×倍率回冲（`TYPE_RETURN_BACK`），**含"余额不足扣到 0"边界**。
- **倍率升级联动**：A 段赠送把成长值顶过门槛 → 等级自动升银卡(120%)，B/D 的期望值按"操作当下等级倍率"计算（**测试夹具要在赠送发生前锁定倍率**，否则断言漂移）。

> **E2E 可重复**：`member.integration / growth / history_integration` 等只增不减字段，夹具每段显式归零。

## 7. 已知边界

1. **退款为 Mock**：无真实支付通道，`payment` 仅标记退款状态与金额/时间，不产生真实资金流。
2. **成长值不回冲**：退货只回冲积分，成长值（含其触发的等级）不回退。
3. **自动确认收货为轮询**：非精确定时（最大误差 ≈ 一轮间隔），对"天"级场景足够。
