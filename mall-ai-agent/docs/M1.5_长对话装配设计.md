## 1. 为什么必须做（现状与问题）

### 1.1 现状：裁剪发生在「写盘时」，且是覆盖回写

现在的链路（`app/main.py` → `app/sessions.py` → `app/store.py`）：

```python
# main.py（非流式与流式的写法一致）
messages = sessions.get_history(session_id, member_id) + [HumanMessage(req.message)]
result = agent.invoke({"messages": messages})
sessions.set_history(session_id, result["messages"], member_id)   # ← 写回

# sessions.py
def set_history(session_id, messages, member_id=None):
    store.save_messages(session_id, _to_dicts(_trim(list(messages))), member_id)  # ← 裁剪结果直接落盘

# store.py
def save_messages(sid, messages, member_id=None):
    ...
    pipe.set(_k_messages(sid), json.dumps(messages, ensure_ascii=False), ex=SESSION_TTL)  # ← 覆盖整键
```

一句话：**`_trim()` 的输出被当作"新的事实"覆盖写回 Redis**。被裁掉的轮次在 Redis 里也不存在了。

### 1.2 六个问题，按严重度排序

| # | 问题 | 现象 / 后果 | 严重度 |
| --- | --- | --- | --- |
| 1 | **不可逆**（策略与数据耦合） | 裁剪结果覆盖回写，原始轮次当场消失。将来想换更好的摘要/RAG 方案，**素材已经没了**，无法回放 | 🔴 最高 |
| 2 | **只丢不压** | 超预算就从最旧整轮丢弃。跨天的"预算 3000、要降噪"被裁掉后，助手无法再引用，且无从恢复 | 🔴 高 |
| 3 | **token 估算失真** | `_est_tokens` 用 `len//2`——它**两头都不准**：中文被**低估**约 2 倍（中文≈1 token/字，却按 2 字符/token 算），英文/JSON 被**高估**约 1.6 倍（英文≈3.3 字符/token）。于是中文会话过早压缩、英文 JSON 又白占预算 → 预算形同虚设 | 🟠 中 |
| 4 | **工具 JSON 是 token 黑洞** | 一次 `search_products` 回 20 条商品 JSON，而 LLM 真正用的只是 `show_products` 认可的那 3–5 个 id | 🟠 中 |
| 5 | **整读整写 O(n)** | 每轮 `GET` 整个会话 → `json.loads` → `json.dumps` → `SET` 整个会话，越长越贵（Redis 单 value 也在膨胀） | 🟠 中 |
| 6 | **无优先级** | "我要买这个"与一次失败的搜索，被裁概率相同；关键参数（skuId / 地址 / 预算）没有保护 | 🟡 低 |

### 1.3 一个容易误解的前提

**问题不是"窗口不够"。** DeepSeek 的上下文窗口远大于当前的 `SESSION_TOKEN_BUDGET=6000`。6000 是刻意保守——因为上下文越长：**成本越高、首字延迟越大、注意力越涣散**。

> 所以目标不是"尽量全塞"，而是**让上下文"短而相关"**。
> M1.5 的立场：**用"压缩信息"换 token，而不是用"丢信息"换 token。**

## 2. 核心原则（四条铁律）

1. **事实源不可变**
   `ai:session:{sid}:messages` 是**唯一事实源**，追加写。**没有任何压缩路径会修改或删除它**（唯一例外是 §4.3 的"达上限裁剪"，且带前置条件）。

2. **压缩只是"装配视图"**
   摘要、工具外置、折叠引用**都是派生缓存**：丢了只是"回到更啰嗦的装配"，不会丢事实。派生键全部可重建、可丢弃。

3. **便宜优先，LLM 最后**
   手段按成本排序：**桩化 < 折叠 < LLM 摘要**。因为 LLM 摘要最贵、最慢、**有损且可能失败**，所以放最后一级。

4. **可回滚**
   摘要是**影子副本（shadow）**：先写派生、校验通过才更新索引；失败/质量差 → 丢弃影子，回退上一级装配。因为"压缩后的摘要和完整信息是有差别的"，所以**原文永远在，随时可核**。

## 3. 四级降级装配（T0 → T3）

装配的函数签名（替换现在的 `_trim`）：

```python
def assemble(sid: str, member_id, incoming: list[BaseMessage]) -> list[BaseMessage]:
    """从事实源装配本轮 prompt。逐级降级，够用即止。"""
```

### 3.1 T0 原样

- **条件**：`est(全量 + incoming) ≤ BUDGET`
- **动作**：直接用全量，零额外成本。
- 绝大多数短会话停在这一级。

### 3.2 T1 工具结果标记化

> 对应你的主张：**"优先把工具返回结果在对话里只保留标记"**

- **适用范围**：**只处理温区/冷区**（热区之外的）历史 `ToolMessage`。
  **热区（最近 K 轮）的工具消息必须保原文**——LLM 正在用它回答，给个空标记它就会编。
- **机制**：
  1. 把该条 `ToolMessage` 的完整 JSON 外置到 `ai:toolres:{sid}:{msg_id}`（TTL 同会话）；
  2. 对话里那条消息的 `content` 换成**引用桩**：
     ```json
     {"_tool": "search_products", "_n": 20, "_ids": [28, 27, 19], "ref": "toolres:ab12cd"}
     ```
- **桩的硬要求**：必须携带"让 LLM 复述结论所需的**最小事实**"——商品 **id、名称、价格**。
  因为指代（"买第一款"）只需要 id 就能定位；要细节时 LLM 可重新调 `get_product_detail` 取回（**标记 + 可回查**）。
- **预期收益**：省 ~60%（示意）。
- **风险**：桩字段给少了 → 指代断链；给多了 → 白省。**字段集需实测确定**（§10）。

### 3.3 T2 中间轮折叠（保头尾）

> 对应你的主张：**"保留消息前三条和后几条，中间存储同时保留标记"**

- **保留头部**：最早 `HEAD_KEEP_ROUNDS`（默认 2–3 轮）。最早的消息常含**初始偏好 / 总目标**，丢了影响全局。
- **保留尾部**：最近 `HOT_ROUNDS`（默认 6 轮），含工具消息原文。
- **折叠中间**：整轮替换为占位消息：
  ```
  [第 x–y 轮，共 n 条消息，已折叠；ref=history:{sid}:{start}-{end}]
  ```
- **保头的双重好处**：
  - 语义上——总目标常在最前；
  - 工程上——前缀稳定，**利于 DeepSeek 前缀缓存**。
- **钉住规则（必须）**：**含"未消费订单草稿"的轮次永不被折叠**，否则会把进行中的下单劈开。
- **预期收益**：再降到 ~3k（示意）。

### 3.4 T3 LLM 分段摘要

> 最后手段。仅当 T2 后仍超预算时启用。

- **分段链（不是单段滚动）**：
  - 每 `SUMMARY_SEG_ROUNDS`（默认 8）轮压成一段 `ai:summary:{sid}:seg:{i}`；
  - 段数超过阈值后，把若干段再滚压成更高层的段；
  - **增量、可滚**，不像单段滚动那样"每次全量重算、越压越糊"。
- **注入形态（关键）**：摘要作为**一条明确标注的"背景记忆"消息**注入，位于 `system` 之后、热区之前：
  ```
  【历史摘要 · 非用户原话】用户此前关注：……（预算约 3000 元，偏好降噪）
  ```
  **绝不能伪装成用户发言**——否则 LLM 会当成"用户说过"并开始引用用户从未说过的话，这是比遗忘更严重的幻觉事故。
- **触发**：**惰性异步**（见 §6）。
- **原文不动**：摘要只是**新增**一个 key，原文照旧完整保留。

### 3.5 降级顺序与停止条件

```python
def assemble(sid, member_id, incoming):
    full = load(messages)                       # 事实源，只读
    if est(full + incoming) <= BUDGET:          # T0
        return full + incoming
    view = stub_tools(full)                     # T1（只动温/冷区工具消息）
    if est(view + incoming) <= BUDGET:
        return view + incoming
    view = fold_middle(view)                    # T2（保头尾 + 钉住 draft）
    if est(view + incoming) <= BUDGET:
        return view + incoming
    view = inject_summaries(view)               # T3（注入已有摘要段，必要时异步补压）
    return view + incoming                      # 兜底：即使仍超，也发（预算不是硬闸）
```

要点：**逐级降、够用即止**；预算是"尽量满足"的软约束，不是会报错的硬闸——宁可略超，不能因装配失败而让对话挂掉。

## 4. 存储设计

### 4.1 Redis key 一览

| key | 类型 | TTL | 性质 | 说明 |
| --- | --- | --- | --- | --- |
| `ai:session:{sid}:messages` | **List**（每条消息一个 JSON 元素） | 7d 滑动 | **事实源** | 全量原文，`RPUSH` 追加；唯一可被裁剪的键（仅 §4.3） |
| `ai:session:{sid}:meta` | Hash | 7d | 事实源 | `owner / lastActive / rounds / msgCount / assemblyLevel` |
| `ai:toolres:{sid}:{msg_id}` | String(JSON) | 7d | 派生·可丢 | 工具结果外置全文（T1 用） |
| `ai:summary:{sid}:seg:{i}` | String(JSON) | 7d | 派生·可丢 | 第 i 段摘要（T3 用），含 `digest` |
| `ai:summary:{sid}:index` | Hash | 7d | 派生·可丢 | 段号 → 覆盖的消息区间 + digest，供校验与回滚 |
| `ai:assembly:{sid}:last` | String(JSON) | 15m | 诊断 | 上次装配用了哪级 / 哪些 key（排查用） |
| `ai:lock:summ:{sid}` | String（`SETNX`） | 30s | 锁 | 单飞锁，防多 worker 并发重复压缩 |

> **为什么 `messages` 从 String 改成 List**：
> ① `RPUSH` 追加天然 O(1)，修掉问题 5 的"整读整写 O(n)"；
> ② 装配时只需 `LRANGE` 取"尾部 K 条 / 头部 N 条"，不必反序列化整个会话；
> ③ §4.3 的"删最旧"就是 `LTRIM`，语义清晰。

### 4.2 写入路径（追加式）

```python
# store.py 新增，替代 save_messages 的"覆盖整键"
def append_messages(sid, dicts, member_id=None):   # 只追加
def trim_oldest_rounds(sid, n, member_id=None):    # 仅上限裁剪时调用（§4.3）
def load_range(sid, start=-HOT, stop=-1):          # 取区间，不必全量
```

`sessions.set_history()` 不再 call `_trim()` —— **写入永不变形**。

### 4.3 上限策略：达上限才删最旧（已实施，M1.5.4）

"原文永不删除"与"Redis 不能无限增长"存在矛盾，故设上限：

- 上限：`SESSION_MAX_ROUNDS`（默认 **300** 轮）或 `SESSION_MAX_BYTES`（默认 2 MB），先到先算。
- **触发裁剪的前置条件（硬性）**：要删的那最旧一轮**必须已被摘要覆盖**。否则**不删**——宁可本轮超限，等异步补压后下一轮再删（`maybe_trim` 返回 `{"blocked": True}` 并告警）。
- 实现：`summarize.maybe_trim()` 编排 + `store.trim_oldest_messages()` 落 `LTRIM`；审计记录写 `ai:retention:{sid}:last`（删了哪几轮、由哪些摘要段兜底、当时体积）。
- 这是**唯一真正丢数据的地方**，且一定有摘要兜底。

**两个关键设计（都是"裁剪不破坏摘要"的前提）**

1. **轮号是绝对的**：`meta.rounds` 是会话诞生以来的**累计**轮数（裁剪不动它），`meta.trimmedRounds` 是已从头部删掉的轮数，于是当前第 k 条轮 = 绝对第 `trimmedRounds + k` 轮。
2. **摘要校验改用轮号，而不是消息下标**：段记录里的 `mFrom/mTo` 只是调试信息。若拿它校验，裁剪后下标整体前移就会**指向别的消息**、把好段误判失效（静默丢摘要）。改成"轮号 − trimmedRounds → 当前下标"后，**裁剪无需改写任何段记录**。源轮已被裁掉、无法校验的段打 `pruned=True`，装配侧直接信任它（剔除后它是这些轮唯一的记录）。

## 5. 回滚协议

M1.5 的可靠性来自"派生与事实分离"，所以回滚是**天然的**，不需要复杂补偿：

| 环节 | 规则 |
| --- | --- |
| **写入顺序** | ① 写派生（`toolres` / `summary:seg:i`）→ ② 校验 `digest` 与源区间一致 → ③ 才更新 `summary:index`。任一步失败 → 不更新索引，等于没压过 |
| **装配时校验** | 读摘要段时校验 `digest`；不匹配 / 反序列化失败 → **跳过该段**，退到 T2/T1，并投递一次异步重压 |
| **压缩失败** | 本轮直接用 T1/T2 兜底，用户无感；不写任何索引 |
| **人工回滚** | 直接 `DEL ai:summary:{sid}:*` → 下轮装配自动退回 T2。**功能不受影响，只是 prompt 变长** |
| **永不发生的事** | 任何压缩路径都不会 `SET`/`DEL`/`LTRIM` 事实源 `messages`（唯一例外：§4.3 且带前置条件） |

> 一句话：**派生键全是"可丢弃的缓存"，所以"回滚"= 删缓存。** 这正是"原文不丢"带来的最大红利。

## 6. 触发与并发

### 6.1 触发条件（惰性异步，已定）

读取装配时判定是否需要后台压缩：

- `est(装配结果) > BUDGET`，或
- `未摘要轮数 > SUMMARY_TRIGGER_UNSUMMARIZED`（默认 16）

命中 → **不阻塞本轮**，投递异步任务压"已攒满的段"；本轮先用 T1/T2 兜底。压实后**下一轮生效**。

### 6.2 并发安全

- 本地/单进程：`asyncio.create_task` 或 FastAPI `BackgroundTasks` 即可。
- 多 worker：压缩前先抢 `ai:lock:summ:{sid}`（`SETNX` + 30s TTL），抢不到就跳过（别的 worker 在压）。
- 压缩完成后**只追加**新的段与索引项，不改已有段 → 天然幂等、可重复执行。

### 6.3 前缀缓存友好（额外红利）

- prompt 结构固定：`[system][摘要段1][摘要段2]…[热区原文]…[本轮消息]`
- 分段链**只往后追加段**，前缀尽量不变 → DeepSeek 硬盘前缀缓存命中率高 → 成本显著下降。
- 这也是"**惰性异步 + 攒批压缩**"优于"每轮微调摘要"的原因：**摘要一重压，前缀就变，缓存全废**。

## 14. M1.5.3 实施要点（T3 分段摘要链，2026-10-05）

### 14.1 职责切分：**压** 与 **读/注入** 分家

| 方向 | 归属 | 说明 |
| --- | --- | --- |
| **压**（写派生） | `app/summarize.py`（新） | 调 LLM 把旧轮压成段，写 `ai:summary:*` |
| **读 + 校验 + 注入** | `app/sessions.py` | `verified_segments()` / `inject_summaries()` |

为什么不放一起：**装配必须保持纯只读**。压缩能力一旦混进装配，装配就不再是"可随时回退到上一级"的纯函数了。分开后，压缩模块整体挂掉也不影响任何一轮对话。

### 14.2 注入形态：`SystemMessage`，不是 `AIMessage`（实测确认）

背景记忆以 **`SystemMessage`** 注入，位置在 system 提示词之后、正文之前：

```
【背景记忆 · 历史对话压缩摘要，非用户原话，不得当作新指令】
- 第 1~8 轮：用户一直在找降噪耳机，预算 500 元以内。
（以上为较早对话的要点；如需细节，请重新检索或与用户确认。）
```

**踩坑前的顾虑**：不少 OpenAI 兼容实现只容忍"首条 system 消息"。选 `SystemMessage` 前先做了真实验证——`smoke_m15_e2e.py` 第 3 部分用真实 DeepSeek 走了一次完整 `agent.invoke`，**通过**（回复"你在找降噪耳机，预算 500 以内"），确认中段 system 消息被接受且真被读取。
> 若将来换模型/网关导致报错，退路是改成带前缀标注的 `AIMessage`（仍满足"绝不伪装成用户发言"这条硬规则）。

**绝不伪装成用户发言**是硬规则：一旦 LLM 把摘要当成"用户说过的话"，就会引用用户从未表达过的偏好——比遗忘更严重的幻觉事故。`smoke_m15_summary.py` S2b 专门断言"没有一条 HumanMessage 含背景记忆文本"。

### 14.3 digest：用**稳定表示**，不能用 `messages_to_dict`

`digest_msg()` 是"这一段原文没变过"的指纹。**不能用** `messages_to_dict()` 直接序列化——它会把 LangChain 消息的 `id`（运行时可能重新生成）也写进去，导致同一会话读两次 digest 不同、摘要段被误判失效。所以 `_canonical()` 只挑稳定字段（type/content/tool_calls/tool_call_id/name）。

### 14.4 校验即回滚：`verified_segments()` 的三道关

| 关 | 不过时 |
| --- | --- |
| 段本体存在且含 text | 跳过 |
| 索引 digest == 段 digest | 跳过（索引/段不匹配的半成品） |
| 源区间仍在且 `digest_msg(源切片)` == 段 digest | 跳过（**源动过 → 摘要已过期**） |

第三关在"源区间已被裁剪"时无法校验（消息已不在），此时**信任该段**——它是唯一记录。人工回滚更简单：`store.clear_summaries(sid)` → 下轮装配自动退回 T2。

### 14.5 触发：惰性异步 + 单飞 + "攒批"

- `maybe_schedule()` 三步门控（越靠前越便宜）：配置开关 → **O(1) 读 meta 轮数/覆盖进度** → 抢单飞锁。
- 为让门控 O(1)，`meta` 里维护两个计数：`rounds`（追加时按 HumanMessage 条数累加）与 `summRounds`（摘要覆盖到的前缀轮数）。
- **压缩在 daemon 线程**里做，本轮不等待；压实后下一轮生效。单飞锁 `ai:lock:summ:{sid}`（SETNX + 90s，Lua 比对 token 释放）。
- **攒批**：正常情况下攒够 `SUMMARY_TRIGGER_UNSUMMARIZED`(16) 轮才压；**只有装配已降到 T3（超预算）才提前到"够一段就压"**。理由见 §6.3——摘要一重压前缀就变，DeepSeek 前缀缓存全废，所以宁攒批。
- **失败即停**（`break` 而非 `continue`）：保证"已摘要轮数"始终是**前缀**，否则 `summRounds` 门控会说谎、还会在覆盖区间里留空洞。

### 14.6 分段链滚压

段数 > `SUMMARY_ROLLUP_SEGS`(12) → 把最旧的 12 段滚压成一段 `level+1` 的段（循环直到不超）。滚压段的 digest 仍按**原始消息**的并集区间计算，所以校验逻辑无需特殊处理。

| S3 | 人工回滚（删摘要 → 退回 T2，原文不动） |

## 15. M1.5.4 实施要点（上限裁剪 + token 精算，2026-10-05）

### 15.1 上限裁剪：先把"删"和"压"分开

| 动作 | 归属 | 触发 |
| --- | --- | --- |
| **压**（写派生摘要） | `summarize.maybe_schedule` → 后台线程 | 每轮读后判定，攒批 |
| **删**（真删原文） | `summarize.maybe_trim` → 同步、O(1) 门控 | 每轮**写后**判定 |

`maybe_trim` 的三段式：

1. **O(1) 门控**：读 `meta.rounds` / `meta.trimmedRounds` / `meta.bytes`（都是计数，不必 LRANGE）。没超就立刻返回 `{}`——绝大多数轮次到此为止。
2. **可删前缀**：只有 `[trimmedRounds, summRounds)` 这一段轮是"已被摘要覆盖"的，最多只能删这么多。`deletable == 0` → 返回 `{"blocked": True}` 并告警（**宁可先超限，也不丢唯一记录**）。
3. **删多少**：按"轮数超了多少"与"字节超了多少（除以每轮均值折算）"取较大者，再 `min(deletable)`，然后 `LTRIM` + 累加 `trimmedRounds`。

审计记录写 `ai:retention:{sid}:last`：`trimmedRounds / trimmedMessages / fromRound / toRound / coveredBy / rounds / bytes`。

### 15.2 token 精算：字符类别启发式（零新依赖）

不引 `tiktoken`（DeepSeek 的 tokenizer 本就不同，引它只是"伪精确"），改用分类估算，**两类都取保守侧**：

```
tokens ≈ CJK字符数 × 1.0   +   其他字符数 / 3.3      （再加 1）
```

实测对比（`smoke_m15_retention.py` R8）：

| 样本 | 字符数 | 旧 `len//2` | 新估算 | 说明 |
| --- | --- | --- | --- | --- |
| 纯中文 | 400 | 200 | 401 | 旧法**低估**一半 |
| 英文 JSON | 4230 | 2115 | 1282 | 旧法**高估**约 1.6 倍 |
| 混合（工具消息） | 1533 | 766 | 469 | 落在合理区间 |

> 影响：中文会话的降级会比以前**更早**触发（因为以前低估），英文 JSON 则更省预算——这正是"预算可信"该有的表现。预算是软约束，不会因此让对话挂掉。

### 15.3 裁剪为什么不会弄坏摘要（本轮最关键的一点）

段记录里原本存了 `mFrom/mTo`（保存时的**消息下标**）。上限裁剪从头部 `LTRIM` 后，所有下标整体前移——若还用它们校验 digest，会**指到别的消息**上、把好段判成失效（表现为"裁剪后摘要凭空消失"）。

改法：**校验只认绝对轮号**。

```
当前下标的第 k 条轮  ==  绝对第 (trimmedRounds + k) 轮
判断顺序：无轮号(老格式) → 信任 ／ pruned 或 rTo ≤ trimmed → 信任（源已裁，它是唯一记录）
          ／ 否则按轮号换算回当前下标，重算 digest 比对
```

收益：**裁剪无需改写任何段记录**（只 `LTRIM` + `INCR trimmedRounds`），也就没有"改写失败 → 摘要全废"的失败面。

### 15.4 新增验收：`scripts/smoke_m15_retention.py`（19 项）

| 组 | 覆盖 |
| --- | --- |
| R1 | 字节计量：追加 / 再追加 / 裁剪后 meta.bytes 与真实载荷**逐字节一致**；重置重算且 trimmedRounds 归零 |
| R2 | 未覆盖不删：超上限但 `summRounds==0` → `{"blocked": True}`，条数不变 |
