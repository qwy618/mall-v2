## 1. 为什么必须做 M1（现状与问题）

### 1.1 病一：会话与草稿活在进程内存里

看现在的代码：

```python
# app/sessions.py —— 会话历史
_sessions: dict[str, list[BaseMessage]] = {}   # 进程内存的字典
_lock = threading.Lock()                        # 用线程锁保并发

# app/orders.py —— 订单草稿
_drafts: dict[str, dict[str, dict]] = {}        # session_id -> draft_id -> 草稿
_lock = threading.Lock()
```

这两个 dict 的后果：

| 场景 | 现象 |
| --- | --- |
| 服务重启 / 热更新（`--reload`） | 用户聊到一半的上下文没了；还没点的「确认下单」草稿也没了 |
| 开 2 个 worker（`uvicorn --workers 2`） | 用户第二句话被路由到**另一个进程** → 它读不到第一句 → 表现为"助手突然失忆"或串到别的会话 |
| 想水平扩容（多实例） | 完全做不到，因为状态钉死在单进程 |

> 一句话：**现在这套只能单进程跑，是玩具；M1 要让它能多进程/多实例。**

### 1.2 病二：金额有**三处**各算一遍（最危险）

这是 M1 里最值钱的修复，也是最容易被忽略的。金额 = 商品总额 − 会员折扣 − 优惠券 − 积分抵扣，其中**会员折扣率、积分余额、券门槛**都归后端管。但现在有三份"算法副本"：

| # | 位置 | 现状 | 风险 |
| --- | --- | --- | --- |
| 1 | **Java `OrderServiceImpl` 第 202–249 行** | 权威算法：`total → promotionAmount（等级折扣）→ couponAmount → integrationAmount（100积分=1元）→ payAmount` | 权威 |
| 2 | **前端 `portal-web/src/views/order/confirm.vue` 第 286–313 行** | 前端**自己重算了一遍**：`promotionAmount`、`beforeIntegration`、`maxUsablePoints`、`integrationAmount`、`payAmount` | ⚠️ 口径要和 Java 逐字对齐，改一处忘一处就漂移 |
| 3 | **AI 助手 `order_tools.py::preview_order`（M0 临时版）** | 只有「单价 × 数量」，**不含**折扣/券/积分 | ⚠️ 确认卡金额与最终下单**必然不一致** |

> 只要三份算法存在，就一定有"确认卡显示 ￥5999，实际扣了 ￥5899"的那一天。用户会投诉。
> **根治办法：后端提供一个"试算"接口，作为唯一权威口径；前端和 AI 都调它，不再自己算。** 这就是 §6 的 `POST /order/preview`。
> **✅ 2026-10-05 已收敛**：第 2、3 份副本均已删除并改为调用 `/order/preview`（助手 M1.3、前端 M1.4）—— 全站金额口径唯一（`OrderServiceImpl.computeAmounts`）。

### 1.3 病三：下单幂等没闭环（助手侧）

后端已经做得很好（债务 23）：`POST /order/token` 取一次性令牌 → `POST /order/create` 带 `submitToken` → Redisson + Lua 原子认领。M0 也把 `place_order` 改成了这个两段式。

但助手侧还差一环 —— **结果回放**。看现在的时序：

```
用户点「确认下单」
  → LLM 调 place_order → 取 token → create → 成功
  → 但客户端超时（网络抖动），前端没收到成功
  → 用户再点一次 / 前端重试 → 第二次 place_order
  → 后端：令牌已被"完成"标记 → 返回同一笔单 ✅（后端没问题）
  → 但助手侧：草稿已被 pop 销毁 → 报 "订单草稿不存在或已失效" ❌
```

后端是对的，**助手把好消息说成了坏消息**。M1 要补：`draftId → orderId` 结果缓存，命中就直接回放首次结果，不报错、也不重复下单。

```

                        │  mall-ai-agent (FastAPI :8090)              │

                        │    │                                        │

                        │    │     └─ tools/*  ← §3.5 只改 preview_order │
                        │    │                                        │
                        │    └─ store.py  ★新增：Redis 门面（唯一入口） │
                        │          ├─ 会话历史  ai:session:*            │
                        │          ├─ 订单草稿  ai:draft:*              │
                        │          └─ 结果回放  ai:draft:result:*        │
                        └───────────────┬─────────────────────────────┘
                                        │
                     ┌──────────────────┴───────────────────┐
                     ▼                                      ▼
        ┌────────────────────────┐            ┌────────────────────────────┐
        │ Redis (192.168.150.128)│            │ mall-portal :8081          │
        │  与 portal 隔离用 db 5  │            │  ★新增 POST /order/preview  │
```

三条主线，对应三个病：

1. **状态外置**（§5）：`sessions.py` / `orders.py` 的 dict → Redis（经 `store.py` 收口）。
2. **金额同源**（§6）：Java 新增 `/order/preview`，与 `/order/create` 共用 `computeAmounts()`；助手 `preview_order` 改调它。
3. **幂等闭环**（§5.5）：草稿一次性 + 结果缓存回放 + DB 唯一键兜底。

## 3. 技术选型与依据

| 技术 | 用在哪 | 为什么选它 / 备选是什么 |
| --- | --- | --- |
| **Redis**（决策 D4） | 会话、草稿、结果缓存 | 天然 TTL（草稿过期不用自己写定时清理）、原子操作（幂等消费）、多进程共享。备选：MongoDB（原 `sessions.py` 注释里写的计划）——但草稿需要"到点自动消失"，Mongo 的 TTL 索引不如 Redis 直观，且项目已有 Redis，不引入新中间件 |
| **redis-py（`redis` 包，同步客户端）** | Python 侧唯一 Redis 客户端 | ① 工具函数是**同步**的（`@tool` 装饰的普通函数），用同步客户端最省心，不必在 sync 工具里 `asyncio.run`；② redis-py 的**连接池线程安全**，可全局一个 client 被多线程（LangGraph 的 executor 线程）共用。备选：`redis.asyncio`——只在 async 端点里更优，但会让 sync 工具变复杂，M1 不采用 |
| **JSON 序列化（不用 pickle）** | 存消息、存草稿 | pickle 反序列化=执行任意代码，缓存一旦被写入（哪怕是低权限）就是 RCE 面。**铁律：只存 JSON。** 消息用 `langchain_core.messages.messages_to_dict` / `messages_from_dict` 官方转换器 |
| **滑动 TTL**（每轮刷新 `EXPIRE`） | 会话 key | 避免"活跃会话被误清"。写入时顺带 `expire(key, 7d)` |
| **Lua / SETNX** | 草稿原子消费 | "读-判-写"三步必须原子，否则并发点两次会双双放行。mall-v2 已用 Redisson `RScript` 做过同样的事（`OrderIdempotentServiceImpl`），助手侧同法 |
| **ContextVar**（已有） | 把 token/session 传给无状态工具 | M0 已验证可用，M1 保持。⚠️ 注意：ContextVar 依赖"上下文的拷贝"，若 LangGraph 换了用线程池执行工具的方式需回归测试（§10 风险） |
| **上下文 token 预算裁剪**（★新增） | 会话历史 | 现在只按条数砍（`MAX_HISTORY = 48`），但工具消息是大段 JSON，48 条完全可能撑爆 DeepSeek 上下文。M1 加"按估算 token 裁剪"，且**必须保持 tool_call / tool_result 成对**（§5.4） |
| **Java：Redisson / MyBatis-Plus / BigDecimal**（均为项目已有） | `/order/preview` | 不做新引入。金额全程 `BigDecimal`，禁止浮点（沿用 `OrderServiceImpl` 现有口径） |

## 4. 状态层 Key 设计（Python 侧）

统一放在 **Redis db 5**（portal 用 db 0；物理隔离，永不误删对方 key），键前缀 `ai:`。

| Key | 类型 | TTL | 存什么 | 谁写谁读 |
| --- | --- | --- | --- | --- |
| `ai:session:{sid}:messages` | STRING(JSON) | **7 天滑动** | LangChain 消息序列（含工具消息） | `store.load_messages` / `store.save_messages` |
| `ai:session:{sid}:meta` | HASH | **7 天滑动** | `memberId` / `lastActive` / `msgCount` | 会话归属校验 |
| `ai:session:{sid}:summary` | STRING | 7 天 | （可选，M3）被裁掉的旧对话摘要 | §5.4 升级项 |
| `ai:draft:{sid}:{memberId}:{draftId}` | STRING(JSON) | **15 分钟** | 订单草稿（下单参数 + 金额快照） | `create_draft` / `get_draft` / `pop_draft` |
| `ai:draft:result:{draftId}` | STRING | **1 小时** | `draftId → orderId`（结果回放） | §5.5 幂等 |
| `ai:quota:{memberId}:{yyyymmdd}` | STRING(计数) | 至次日 | 当日调用数 | **M4 治理用**，M1 只建 key 不启用 |
| `ai:rate:{memberId}:{minute}` | STRING(计数) | 60s | 每分钟限流 | **M4 治理用**，M1 只建 key 不启用 |

> ✅ **实测确认（2026-10-05）**：草稿 key **把 `memberId` 编进 key 空间**（而不是只存在 value 里）——归属由 key 天然保证，别人连"找到"都做不到，Lua 也就能保持最简单的 `GET`+`DEL`（不必在 Lua 里解析 JSON）。

### 4.1 设计要点

- **会话隔离（防"换个 sid 读别人聊天记录"）**：前端生成 `sessionId`（UUID）；服务端在 `meta` 里记 `memberId`。**读历史时校验 `meta.memberId == 当前登录 memberId`**，不一致就当作空会话。未登录会话允许存在（只读商品问答），但一旦要加购/下单必须登录。
- **不把 JWT 长存 Redis**：token 仍由前端每次请求带入（现有做法），服务端只在**单次请求内**使用，不落盘。
- **草稿必须绑 `(sid, memberId)`**：`pop_draft` 时同样校验归属，防止"A 的草稿被 B 消费"。
- **`LAST_ACTIVE` 只用于展示，不参与鉴权**。

### 5.4 ★ 上下文窗口裁剪（补上现有缺口）

现在只按**条数**砍（48 条）。但一条 `search_products` 的工具结果可能是十几条商品的大 JSON，48 条能轻松超过 DeepSeek 的上下文窗口。M1 加第二把尺子：**按估算 token 裁剪**。

**两条铁律（不遵守会让 LLM API 直接报错）：**

1. **`tool` 消息不能单独丢**。一条 `ToolMessage` 必须紧跟它对应的、带 `tool_calls` 的 `AIMessage`。只删 tool 消息 → 报 `tool_call_id not found`。
2. **必须按「轮」整组丢，不能按单条消息丢**。若按单条消息裁剪，很容易出现"保留了助手的回答、却把用户的提问丢了"——上下文只剩半截，LLM 会答非所问。
   → **实现口径：以 `HumanMessage` 为边界切轮**（每条 Human 开启一轮，直到下一条 Human），整轮保留/丢弃。这样一次解决两个问题：上下文连贯 **且** tool 配对天然完整。

伪代码：

```python
def _groups(messages):          # 按轮切分
    groups, cur = [], []
    for m in messages:
        if m.type == "human" and cur:
            groups.append(cur); cur = [m]
        else:
            cur.append(m)
    if cur: groups.append(cur)
    return groups

def _trim(messages, budget=TOKEN_BUDGET, max_msgs=MAX_HISTORY):
    # 前导 system 消息永远保留
    # 从最新一轮往回累计"估算 token"（中文取 len/2，偏保守），
    # 超出预算或条数上限就停止，丢弃更早的整轮
    # 保底：至少保留最后一轮（哪怕它自己就超预算）
```

**M1 做"确定性裁剪"即可**（不调用 LLM，零额外成本）。**升级项（可选，留 M3）**：把裁掉的旧对话用一次 LLM 调用压成一句摘要，存 `ai:session:{sid}:summary`，下轮拼在系统提示里 —— 这样长会话能"记住很久以前聊过什么"。

### 5.5 ★ 幂等闭环（三层防护）

```
                     ┌─ 第 1 层：草稿一次性（Lua 原子消费）
用户点确认 → place_order ─┼─ 第 2 层：结果缓存回放  ai:draft:result:{draftId}
                     └─ 第 3 层：DB orders.submit_token 唯一键（mall-v2 已有）
```

**第 1 层 · 草稿原子消费（Lua）**：解决"连点两次确认"。

```lua
-- KEYS[1] = ai:draft:{sid}:{draftId}
-- 存在则原子取出并删除，返回 JSON；不存在返回 nil
local v = redis.call('GET', KEYS[1])
if v then redis.call('DEL', KEYS[1]) end
return v
```

**第 2 层 · 结果回放**：解决"网络重试 → 第一次其实已成功"。

```python
def place_order(draft_id):
    # ① 先查是否已经下过单（回放）
    if (oid := store.recall_result(draft_id)):
        return _order_result(oid)          # 直接回放，不报错、不再下单

    draft = store.pop_draft(sid, draft_id, member_id)   # 原子消费
    if not draft:
        # 草稿没了且也没有结果缓存 → 说明确实过期或从没生成过
        raise ToolException("订单信息已过期，请重新确认订单")

    # ② 取 token → create（两段式）
    tk = api_post("/order/token")
    oid = api_post("/order/create", body={...draft..., "submitToken": tk})

    store.remember_result(draft_id, oid)   # 记结果，供回放
    return _order_result(oid)
```

> 注意顺序：**先查结果缓存，再消费草稿**。反过来的话，第一次成功后的重试会先拿到"草稿不存在"而误报失败。

**第 3 层 · DB 兜底**：`orders.submit_token` 唯一键（mall-v2 已实现），即便前两层都被绕过，数据库也不会产生第二单。助手侧无需改动。

### 5.6 并发确认保护（前端配合逻辑，M2 落地）

用户连点「确认下单」：

### 6.1 新增接口契约：`POST /order/preview`

> 冻结此契约后，M1.1（Python）与 M1.2（Java）可并行开发。


**响应**（`CommonResult<OrderPreviewVO>`）：

```json
{
  "code": 200,
  "data": {
    "address": { "id": 3, "receiverName": "张三", "phone": "138...", "province": "北京", "city": "北京", "district": "海淀区", "detailAddress": "..." },
```

**行为约定（与 create 的差异，仅此三点）**：

| | preview | create |
| --- | --- | --- |
| 金额计算 | **同一段代码** | **同一段代码** |
| 扣库存 | ❌ 否 | ✅ 是 |
| 订单落库 | ❌ 否 | ✅ 是 |
| 消耗幂等令牌 | ❌ 不消耗 | ✅ 消耗 |
| 核销优惠券 / 扣积分 | ❌ 否 | ✅ 是 |

> **原则：确认卡片上的每一个数字，都必须来自最终下单那条链路的同一段代码。** 这是防金额纠纷的根本手段。

### 6.2 怎么做到"同源"：把 `doCreateOrder` 拆成两段

现在 `doCreateOrder`（第 116–329 行）把「读数据 + 算金额 + 扣库存 + 落库」全揉在一个循环里，**没法直接给 preview 复用**。做法是**纯重构**（不改变 create 的行为，只搬代码）：

**抽 ①：`resolveItems(...)` —— 只读，不扣库存**

```java
/** 把入参 SKU 解析成"含商品信息 + 券适用判断"的行项目，全程只读，不扣库存、不落库。 */
private List<ResolvedItem> resolveItems(Long memberId, List<OrderItemParam> params, Coupon coupon)
```
职责：查 `Sku` / `Product`、校验 `cartItemId` 归属、算 `lineAmount`、判断该行是否属于券适用范围（填 `couponBase`）。
**把现在循环里的"扣库存"单独挪出去**（见 ③）。

**抽 ②：`computeAmounts(...)` —— 纯计算，可复用于 preview / create**

```java
/** 三类优惠一次性算定：会员折扣 → 券 → 积分，与 preview/create 共用（唯一权威口径）。 */
private Amounts computeAmounts(Member member, List<ResolvedItem> items,
                               Coupon coupon, Integer requestedIntegration)
```
职责：`total → promotionAmount → couponAmount（含"券适用小计"门槛校验）→ integrationAmount → payAmount`。
返回一个 `Amounts` 值对象（`total / promotion / coupon / integration / useIntegration / payAmount`）。
**把现在 `5.x` 那整段（第 202–249 行）原样搬进来**，一行口径都不改 —— 这是"同源"的保证。

**抽 ③：扣库存循环（仅 create 调用）**

```java
/** 原子扣库存（仅 create）：UPDATE sku SET stock = stock - n WHERE id = ? AND stock >= n */
private void deductStock(List<ResolvedItem> items)
```

**重构后的 `doCreateOrder`（create）流程**：

```
1. 校验地址归属、取券（同现在）
2. List<ResolvedItem> rows = resolveItems(...)        ← 抽 ①
3. Amounts a = computeAmounts(...)                     ← 抽 ②（含券门槛校验）
4. deductStock(rows)                                   ← 抽 ③（唯一"有副作用"的一步）
5. 落订单 + 项 + 核销券 + 扣积分 + 分摊 + 清购物车（同现在）
6. afterCommit：失效购物车缓存 + finish 令牌 + MQ（同现在，别动）
```

**新增的 `preview`（preview）流程**：

```
1. 校验地址归属（addressId 为空则取默认地址）
2. List<ResolvedItem> rows = resolveItems(...)   ← 复用
3. Amounts a = computeAmounts(...)                ← 复用（金额与 create 逐分一致）
4. 组装 OrderPreviewVO 返回（不扣库存、不落库、不碰令牌）
```

> 重构的验收：**改完先跑一次原来的下单 E2E，确认 `create` 行为一字不差**，再加 preview。这就是"重构与加功能分开"的纪律。

## 10. 风险与对策

| 风险 | 后果 | 对策 |
| --- | --- | --- |
| **ContextVar 在 LangGraph 线程池执行工具时丢失** | 工具拿不到 token → 误报未登录 | M0 已实测可用；M1 改完必须**回归跑一次 `smoke_m0.py`**（含未登录 → 登录 → 加购链路）。若真丢了，改用显式参数透传（把 token 作为工具入参由 agent 注入） |
| **裁剪消息破坏了 tool_call / tool_result 配对** | LLM API 报 `tool_call_id not found` | 按"消息组"整组丢（§5.4）；裁剪后跑一遍多轮工具对话 |
| **Redis 连不上 / 密码错** | 助手整体不可用 | 启动时 `store.ping()`，失败就**快速失败并打清晰日志**；`.env` 里放 URL，不硬编码 |
| **重构 `OrderServiceImpl` 改变 create 行为** | 下单金额/库存出错 | 严格"先重构、后加接口"；重构后先跑既有下单 E2E，再动 preview |
| **确认卡金额与下单仍可能不一致（并发改价/券过期）** | 用户看到 ¥100 扣了 ¥110 | preview 与 create 同源已消除"算法漂移"；对"预览后价格变了"这类**数据漂移**，做法是下单返回的 `payAmount` 作为最终值**覆盖展示**（前端已有"以真正下单返回为准"的习惯） |
| **db 选择不当误删 portal 数据** | 清空助手状态时误删业务缓存 | 助手固定用 **db 5**；`clear_session` 只按 `ai:` 前缀 + 精确 sid 删，绝不用 `FLUSHDB` |
