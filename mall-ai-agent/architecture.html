四、关键设计亮点（这些是你项目里最值钱的部分）

① 防幻觉的「卡片过滤链路」

LLM 不能直接给前端发卡片。所有商品卡片必须经过：
search_products（拿真实数据）→ show_products（LLM 选 id）→ main.py（用 id 反查真实数据）→ 前端。
LLM 编不出不存在的商品卡片，因为卡片数据始终来自工具返回的真实结果。
SYSTEM_PROMPT 规则 5/6 的工程化落地——把"严禁编造"从口号变成代码强约束。

② 人工确认下单（Human-in-the-loop）

下单分两步：preview_order（算价、生成草稿）→ 用户点按钮 → place_order（消费草稿、真下单）。
草稿一次性使用（orders.pop_draft），LLM 无法篡改购物车 id / 地址 / 金额。
这是 LangGraph 受控流程的雏形——P6 升级到 StateMachine 时这就是面试加分项。

③ JWT 透传的 ContextVar 方案

LangChain 工具签名不能带 session 参数（否则 LLM 会自己填）。用 ContextVar 在 main.py 设置 token，order_tools.py 的 _require_token() 直接拿。
解决"无状态工具调用 + 有状态用户身份"的矛盾——面试常考题。

④ mall 怪癖的统一封装

mall_client.py 把 mall 接口"HTTP 200 但 body.code=401"的反直觉行为统一处理，对外抛 ToolException 给 LLM 看。
真实业务系统集成的常见坑——能讲清这一点说明你做过真集成。

⑤ SSE 事件分层

token / tool / products / product / confirm / order / done / error 8 种事件类型，
前端能做打字机效果、显示"正在搜索…"、渲染卡片、拦截确认——比纯文本流式体验好一个量级。

⑥ SYSTEM_PROMPT 20 条规则

从"严禁编造价格"到"未指定数量先问库存"，把电商客服的高风险场景都覆盖了。
Prompt Engineering 的实战样本——比"我会写 prompt"有说服力得多。

六、改进路线（按秋招面试价值排序）

P5RAG 知识库（商品/评价）

价值：面试最爱问"你做过 RAG 吗"。这是项目从"工具调用"升级到"知识增强"的关键一步。
做什么：
  • 用 Chroma 把商品 description / 评价摘要向量化（用 bge-small-zh 嵌入模型）
  • 新增工具 kb_search(query)：用户问"小米 14 拍照怎么样"时召回相关评价
  • 检索结果作为上下文塞给 LLM，回答有依据
面试加分：能讲 chunking 策略、嵌入模型选型、重排序、引用溯源。
工作量：2-3 天

P6Langfuse 全链路追踪

价值：没有可观测性的 LLM 系统不能上生产。这是"工程能力"的直接证明。
做什么：
  • 接入 Langfuse（开源，自建或云版），记录每次 LLM 调用的 prompt/response/token/cost
  • 每个工具调用打 trace，看到 ReAct 每一步的输入输出
  • 加 Prometheus 指标：QPS、P99 延迟、工具失败率、token 消耗
面试加分：能讲"我怎么定位线上一个 bad case"——95% 候选人答不上来。
工作量：1 天

P7评估集 + LLM-as-judge

价值：工业级 LLM 应用的核心能力。"改 prompt 不会回归"是生产最大风险。
做什么：
  • 写 30 条 golden test：典型 query + 期望行为（应调哪些工具、不应编造什么）
  • 用 DeepSeek 当 judge，给每次回复打分（工具选择正确性 / 幻觉率 / 语气）
  • CI 跑评估集，分数下降就 block 合并
面试加分：直接对标 OpenAI Evals / LangSmith——高级岗位加分项。
工作量：2 天

P8会话持久化（Redis）

价值：现在重启服务所有用户对话历史丢失——这是真实生产事故级别的问题。
做什么：把 sessions.py 的 dict 换成 Redis（hash 结构），orders.py 草稿同样入 Redis 带 TTL。
面试加分：能讲"为什么不用 MySQL 存对话历史"——序列化成本 / 读写模式 / TTL 过期。
工作量：半天

P9LangGraph 受控状态机

价值：从 create_react_agent（自由 ReAct）升级到自定义 StateMachine——下单流程变成强约束状态图。
做什么：定义状态节点 SEARCH → DETAIL → CONFIRM_QTY → CART → PREVIEW → AWAIT_CONFIRM → ORDER，
每个节点限制 LLM 只能调特定工具，跳转条件由代码而非 LLM 决定。
面试加分：能讲"为什么 ReAct 不够用"——LLM 自由度过高，受控流保证合规。
工作量：2 天

P10安全加固

  • CORS 白名单（替换 allow_origins=["*"]）
  • 限流：slowapi 按 token 限流，防恶意刷 token
  • Prompt 注入防御：用户输入做敏感词过滤 + 系统提示用 delimiter 包裹
  • 工具白名单：LLM 不能调未注册的工具（已是默认，但加显式校验）
面试加分：能讲 LLM 安全攻防——OWASP LLM Top 10 现在是热点。
工作量：1 天

P11Docker 化 + CI/CD

  • 写 Dockerfile（python:3.13-slim 基础镜像）
  • docker-compose 一键起 agent + Redis + mall
  • GitHub Actions：lint → test → build → push
面试加分：全栈工程化的最后一公里。
工作量：1 天

P12性能与成本优化

  • 历史消息压缩：超过 20 条用 LLM 总结成 200 字摘要（节省 token）
  • 模型路由：简单意图（查物流）用 deepseek-chat，复杂推理用 deepseek-reasoner
  • 商品搜索结果缓存：Redis 缓存 5 分钟，热门关键词命中率 80%+
面试加分：能讲"LLM 应用的成本结构"——按 token 计费下的工程取舍。
工作量：1-2 天

常被追问的问题 & 你该怎么答

问题回答要点
LLM 会不会编造商品价格？不会。所有商品卡片数据来自工具返回，show_products 只是 LLM 选 id，main.py 用 id 反查真实数据。LLM 没有发卡片的代码路径。
下单怎么防止 LLM 乱来？两步走：preview 生成草稿（cart_id/address_id/amount 都是后端算的），用户点确认后 place_order 只消费草稿、不能改参数；草稿一次性销毁。
JWT 怎么传给工具？LangChain 工具签名不能带 session 参数。用 ContextVar 在请求入口注入，工具调 _require_token() 取。无状态工具 + 有状态用户的解法。
会话历史怎么存？现在进程内 dict（线程锁），P8 升级 Redis。保留 48 条含工具消息，因为"买第一款"这种指代要靠工具消息里的 id。
怎么观测线上问题？现在只能看日志。规划中是 Langfuse 全链路 trace + Prometheus 指标，能定位到每个 LLM 调用的 prompt/response/cost。
怎么防止 prompt 注入？规划中：delimiter 包裹用户输入 + 关键词过滤 + 工具白名单显式校验。OWASP LLM Top 10 这块我也研究过。
为什么用 DeepSeek 不用 GPT？成本（deepseek-chat 比 gpt-4o 便宜 20 倍）+ 国内合规 + 中文电商场景效果好。OpenAI 兼容模式让切换零成本。

项目亮点的"三板斧"

  1. 防幻觉设计：把"严禁编造"从 prompt 规则落到代码强约束（卡片过滤链路）。
  2. 受控流程：下单必须人工确认，草稿机制保证 LLM 无法篡改订单参数。
  3. 工程化思维：从 P0 演进到 P12，每一步有清晰的"为什么这么做"。

秋招投递建议

  • AI/大模型岗（应用层）：突出 RAG（P5）+ 评估集（P7）+ Langfuse（P6）
  • 后端开发岗：突出 LangGraph 受控流（P9）+ Redis 持久化（P8）+ Docker（P11）

  • 大厂（字节/阿里/腾讯）：必须有评估集和可观测性，否则被认为"玩具项目"
